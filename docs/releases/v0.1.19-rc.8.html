Ricochet v0.1.19-rc.8 Release Candidate Notes

A database-transaction and request-budget candidate for safer MVC application work.

On this page Release Identity Application Transactions Controller Instruction Budgets Governance And Packaging CI And Update Channel Current Boundaries Verification Checklist

Date: 2026-07-20

Ricochet v0.1.19-rc.8 advances the candidate line with application-level database transactions and configurable MVC controller instruction budgets. It supersedes RC7 without moving or rewriting that historical release.

Release Identity

  • The Ricochet release and tag identity is 0.1.19-rc.8 and v0.1.19-rc.8.
  • The public GitHub Debian asset is ricochet_0.1.19.rc.8_amd64.deb. Its Debian control version is 0.1.19~rc.8, preserving exact prerelease ordering before stable 0.1.19.
  • The supported desktop application lineage remains the native host shell with a WebView body and Ricochet-managed state. The withdrawn native-control renderer experiment remains outside the supported WebView-only application surface.

Application Transactions

  • MVC database capabilities now expose postfix transaction, begin, commit, rollback, and savepoint methods.
  • transaction commits when its block returns an Ok Result and rolls back when the block returns an Err Result. Transaction-control failures remain explicit Results.
  • Savepoints are completed last-created first. Committing a savepoint releases it; rolling it back restores and releases it without ending the outer transaction.
  • Active Record and direct database-capability calls in one request use the same transaction. SQLite pins its existing connection; PostgreSQL and MySQL/MariaDB use a dedicated transaction connection.
  • An uncaught VM fault triggers best-effort rollback when the request database session is discarded. Database rollback does not undo cookies, logs, HTTP calls, filesystem writes, or other external effects.

Controller Instruction Budgets

  • MVC controllers default to 250000 VM instructions per request, configured with controller_instruction_limit under [web].
  • Operators retain a deployment ceiling through rco serve --max-controller-instructions, which defaults to 1000000. An app cannot raise its own budget above that ceiling.
  • Limit faults report used and configured instructions. Successful actions emit a warning at 80 percent usage, and staged response, session, and log effects are copied out only after controller success.

Governance And Packaging

  • Ricochet first-party source, documentation, assets, crates, packages, and editor metadata remain under the Apache License 2.0 (Apache-2.0).
  • Locked dependency disclosures continue to ship as THIRD_PARTY_LICENSES.html and THIRD_PARTY_NOTICES.txt.
  • Third-party notice generation invokes the installed cargo-about executable directly so strict PowerShell validation is not derailed by unrelated Cargo warnings.
  • Windows release packaging now derives tracked documentation paths without requiring the PowerShell 7-only Path.GetRelativePath API.
  • The public Learn manual now covers 372 live words, including all five application transaction methods.
  • The candidate retains mixed numeric correctness, bounded cycle handling, release probe coverage, and clean tracked-source packaging from prior hardening.
  • The Windows installer continues to validate installed binaries, docs, examples, notices, registration, shortcuts, and uninstall ownership boundaries.

CI And Update Channel

  • CI builds and smokes Windows, Linux, Debian, macOS arm64, and macOS x64 artifacts before publication.
  • The release workflow audits exact asset names, sizes, SHA-256 digests, checksums, manifests, and freshly downloaded bytes before publishing its draft.
  • v0.1.19-rc.8 is a GitHub prerelease, is not marked latest, and publishes UPDATE-CHANNEL-candidate.json.
  • Candidate artifacts use dry-run signing and notarization reports. Stable production signing remains gated by external Windows, Linux, and macOS credentials.

Current Boundaries

  • The hosted workflow must still prove the exact tag, public prerelease state, platform artifacts, checksums, manifests, and candidate update metadata.
  • SQLite transaction behavior is exercised locally. Live PostgreSQL and MySQL/MariaDB acceptance requires separately configured provider endpoints and credentials.
  • Application transactions cover database state only; coordinated transactions across HTTP, files, cookies, sessions, and logs are not implied.

Verification Checklist

Before creating the v0.1.19-rc.8 tag, run the repository gates from a clean checkout:

$version = "0.1.19-rc.8"

cargo metadata --locked --format-version 1
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cargo audit --deny warnings
pwsh -NoProfile -File .\scripts\validate-release-version.ps1
pwsh -NoProfile -File .\docs\reference\validate.ps1
pwsh -NoProfile -File .\scripts\validate-learn-manual.ps1 -RequireWordCoverage -RequireJekyllRawBlocks
pwsh -NoProfile -File .\scripts\validate-license-governance.ps1
pwsh -NoProfile -File .\scripts\acceptance.ps1

$releaseOut = Join-Path (Resolve-Path .\target).Path "rc-prep-smoke\$version\release-windows"
pwsh -NoProfile -File .\scripts\package-release.ps1 -Version $version -Target windows-x64 -OutDir $releaseOut -RequireInstaller -SigningMode dry-run
pwsh -NoProfile -File .\scripts\validate-release-artifacts.ps1 -Target windows-x64 -OutDir $releaseOut -PackageVersion $version -RequireInstaller
pwsh -NoProfile -File .\scripts\validate-store-packaging.ps1 -Target windows-x64 -OutDir $releaseOut -PackageVersion $version

After the release workflow completes, separately verify the published prerelease, tag commit, uploaded assets, combined checksums, platform manifests, signing-status reports, Debian control version, and candidate update-channel metadata.
