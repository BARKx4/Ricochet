Ricochet v0.1.19-rc.5 Release Candidate Notes

A reconciled release-candidate snapshot of the WebView application surface, runtime fixes, governance, documentation, and packaging gates.

On this page Release Identity And WebView Lineage Runtime Correctness And Cycle Safety Governance, Learn, And Packaging Installer CI And Update Channel Current Boundaries Verification Checklist

Date: 2026-07-11

Ricochet v0.1.19-rc.5 advances the v0.1.19 candidate line without rewriting any previously published candidate record. It reconciles the supported WebView-only application surface with the runtime, documentation, licensing, and release-pipeline work completed since the previous immutable candidate.

Release Identity And WebView Lineage

  • The supported desktop application lineage is the native host shell with a WebView body and Ricochet-managed state. The public entry points remain rco gui, rco package --gui, and the rco-gui launcher.
  • The withdrawn native-control renderer experiment is not part of this candidate's application surface. WebView windows, shell services, menus, dialogs, clipboard operations, tables, and split panes remain the supported path.
  • rco --version and rco -V now report the package version, giving release probes a direct identity check.

Runtime Correctness And Cycle Safety

  • Mixed integer and floating-point equality, ordering, and clamp bounds now use exact numeric comparison rules instead of first rounding integers through a floating-point conversion. Fractional values and infinities retain their ordering semantics, while unordered NaN bounds produce an error rather than a panic.
  • Array, list, map, and set traversal now detects reference cycles. Structural comparison, membership, set mutation, and debug formatting terminate safely instead of recursing without a bound.
  • JSON, image, WebView, and MVC serialization reject true cycles with path-aware diagnostics and do not leave partial image or GUI output artifacts behind. Shared acyclic subgraphs remain serializable.
  • The release probe set covers both CLI version flags and the settings-loader example linked from the tracked Learn manual.

Governance, Learn, And Packaging

  • Ricochet first-party source, documentation, assets, crates, packages, and editor metadata now identify the project under the Apache License 2.0 (Apache-2.0), with repository contribution, security, support, and license-governance checks kept in the release gate.
  • Dependencies retain their own licenses. Their deterministic locked, multi-target disclosures ship as THIRD_PARTY_LICENSES.html and THIRD_PARTY_NOTICES.txt; snapshot validation regenerates both files and rejects unresolved licenses or drift before packaging.
  • Learn chapter 22 and the word-coverage inventory now cover 18 supported WebView app-kit and shell-service words for toolbars, sidebars, tabs, split panes, tables, forms, status areas, menus, app documents, pickers, clipboard access, and external URLs. PTY examples also close spawned sessions during cleanup.
  • Release staging uses a clean tracked-source inventory, so untracked local files cannot silently enter a source or platform package.
  • Candidate update validation implements exact SemVer prerelease ordering, including arbitrary-size numeric identifiers, numeric-before-alphanumeric precedence, identifier length rules, and stable-release precedence over a prerelease.

Installer CI And Update Channel

  • The CI workflow is configured with a disposable Windows installer smoke: it builds the NSIS installer, installs to a unique runner-temporary location, validates installed binaries and version output, checks documentation, examples, and notices, exercises WebView packaging and export outside the checkout, inspects per-user registration and shortcuts, then runs the normal silent uninstaller and checks cleanup.
  • Package validation requires the third-party notice bundles at their exact portable, installer, Debian, and macOS package paths.
  • Debian prerelease filenames and control metadata use 0.1.19~rc.5 ordering while the Ricochet release identity remains 0.1.19-rc.5, so the candidate upgrades normally to stable 0.1.19.
  • Every current Debian launcher declares the GTK 3, WebKitGTK 4.1, and libxdo3 runtime dependencies required by its ELF metadata, with clean-runner checks covering both basic and WebView downstream packages.
  • SemVer prerelease tags such as v0.1.19-rc.5 remain GitHub prereleases, are not marked latest, use dry-run signing and notarization, and write UPDATE-CHANNEL-candidate.json with SHA-256 verification metadata.

Current Boundaries

  • This repository snapshot prepares a candidate identity only. It does not itself create a tag or publish packages; promotion still requires the hosted release audit to pass against the exact commit selected for release.
  • Stable production publishing still requires external credentials for Windows Authenticode, Linux GPG, and macOS signing and notarization. Those production signing paths are intentionally outside the candidate dry-run.
  • The candidate channel remains separate from the stable channel. Promote only after the repository checks and native-platform artifact smokes complete against the exact commit selected for release.

Verification Checklist

Before creating the v0.1.19-rc.5 tag, run the repository gates from a clean checkout:

$version = "0.1.19-rc.5"

cargo metadata --locked --format-version 1
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\validate-release-version.ps1
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\docs\reference\validate.ps1
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\validate-learn-manual.ps1 -RequireWordCoverage -RequireJekyllRawBlocks
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\validate-license-governance.ps1
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\acceptance.ps1

$releaseOut = Join-Path (Resolve-Path .\target).Path "rc-prep-smoke\$version\release-windows"
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\package-release.ps1 -Version $version -Target windows-x64 -OutDir $releaseOut -RequireInstaller -SigningMode dry-run
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\validate-release-artifacts.ps1 -Target windows-x64 -OutDir $releaseOut -PackageVersion $version -RequireInstaller
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\validate-store-packaging.ps1 -Target windows-x64 -OutDir $releaseOut -PackageVersion $version

After any future release workflow completes, separately confirm its hosted job result and inspect the uploaded artifacts, checksum file, manifests, signing-status reports, notice bundles, and candidate update-channel metadata. Configuration in this snapshot is not evidence that a hosted release run passed.
