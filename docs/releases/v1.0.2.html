Ricochet v1.0.2 Release Notes

A stable patch release for bounded PostgreSQL connection reuse, faster bytecode calls, and security repairs.

On this page Release Identity Runtime And Security Stable Contract Packaging And Updates Verification Checklist

Date: 2026-10-15

Ricochet 1.0.2 reduces transaction connection overhead and VM allocation while preserving the Ricochet 1.0 language, instruction accounting, debugger checks, and application validation. It also includes the pending v1 security repairs and updated vulnerable dependencies.

Release Identity

  • The stable release and tag identities are 1.0.2 and v1.0.2.
  • The Linux package is ricochet_1.0.2_amd64.deb with Debian control version 1.0.2, providing a stable upgrade from 1.0.1.
  • Read the v1.0.1 release notes for the random initialization fix and the v1.0.0 release notes for the original stable contract and platform boundaries.

Runtime And Security

  • PostgreSQL transaction connections are reused through a bounded pool: eight transaction connections per database root plus its autocommit connection by default. The Rust embedding API supports capacities from 1 to 64. Checkout and connection establishment share a ten-second deadline; rollback and DISCARD ALL cleanup have a five-second deadline.
  • Transaction clones retain exclusive leases. Queries serialize with finish, stale finished handles reject operations, and failed or cancelled cleanup evicts the connection. Session abandonment delegates PostgreSQL cleanup without blocking the destructor. Uncertain writes are never retried automatically.
  • Bytecode callables share immutable compiled bodies, avoiding deep copies of unexecuted code. Inactive debugger checks avoid allocating a breakpoint key. Serialized images retain the existing representation; breakpoints, stepping, caller-stack errors and callable replacement retain their checks.
  • Rust embedders constructing BytecodeCallable with a struct literal must adapt its public chunk field to Arc<Chunk>. The constructor and Ricochet source/image formats remain compatible.
  • Deferred secret HTTP execution enforces HTTPS-only transport. Test-host clients trust only their fixture CA while retaining certificate-chain and hostname validation; GUI session capture and HTTP/stream regressions use that validated TLS path. Positive-control leak scanning can include an exact retained release artifact.
  • The vendored GLib 0.18 security backport repairs Variant string iterator lifetime handling and removes the corresponding advisory exception. The lockfile also updates rustls to 0.23.46 and quinn-proto to 0.11.18. Existing unrelated advisory policy remains explicit.
  • CI includes real PostgreSQL lifecycle, capacity, cancellation, failed finish and cleanup-isolation tests, plus the optimized Linux GLib regression. Generated third-party notices follow the active dependency graph.

Stable Contract

The 1.0.0 WebView-only application surface, Apache-2.0 licensing, and Learn manual remain the stable baseline. This patch does not revise the prior mixed numeric correctness, cycle handling, release probe coverage, or clean tracked-source packaging policies.

Packaging And Updates

  • Official packages include LICENSE, THIRD_PARTY_LICENSES.html, and THIRD_PARTY_NOTICES.txt.
  • CI builds and audits the Windows installer, Linux tarball and Debian package, and macOS arm64/x64 archives before publication.
  • Every uploaded asset, including SHA256SUMS.txt, has GitHub keyless build-provenance attestation tied to the release workflow, tag ref, and source commit. The published immutable release has a separate release attestation.
  • The stable update feed is UPDATE-CHANNEL-stable.json. Its verification metadata requires GitHub attestation and SHA-256 on every platform, and advertises Windows Authenticode or Apple notarization only when produced.
  • Windows and macOS packages may be unsigned when platform certificates are unavailable. Their signing reports identify this fallback, and local security prompts may appear.

Verification Checklist

Before creating the annotated v1.0.2 tag, run the repository gates from a clean checkout, confirm GitHub immutable releases are enabled with maintainer credentials, and perform the Windows package check through the same explicit fallback path used by CI:

$version = "1.0.2"

cargo metadata --locked --format-version 1
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cargo audit --deny warnings
$immutable = gh api repos/BARKx4/Ricochet/immutable-releases --jq .enabled
if ($immutable -ne 'true') { throw 'Enable immutable releases before tagging' }
pwsh -NoProfile -File .\scripts\validate-release-version.ps1
pwsh -NoProfile -File .\docs\reference\validate.ps1
pwsh -NoProfile -File .\scripts\validate-learn-manual.ps1 -RequireWordCoverage -RequireJekyllRawBlocks
pwsh -NoProfile -File .\scripts\validate-license-governance.ps1
pwsh -NoProfile -File .\scripts\acceptance.ps1

$releaseOut = Join-Path (Resolve-Path .\target).Path "release-prep-smoke\$version\release-windows"
pwsh -NoProfile -File .\scripts\package-release.ps1 -Version $version -Target windows-x64 -OutDir $releaseOut -RequireInstaller -SigningMode auto
pwsh -NoProfile -File .\scripts\validate-release-artifacts.ps1 -Target windows-x64 -OutDir $releaseOut -PackageVersion $version -RequireInstaller
pwsh -NoProfile -File .\scripts\validate-store-packaging.ps1 -Target windows-x64 -OutDir $releaseOut -PackageVersion $version

After CI publishes the release, independently verify the peeled tag commit, latest published state, each downloaded asset's build attestation, the immutable release and its assets, matching SHA-256 inventory entries, platform manifests and signing reports, Debian version, and stable update-channel metadata. For example:

$tagCommit = git rev-parse 'v1.0.2^{commit}'
$asset = 'ricochet-v1.0.2-windows-x64.zip'
gh attestation verify $asset -R BARKx4/Ricochet --signer-workflow BARKx4/Ricochet/.github/workflows/release.yml --source-ref refs/tags/v1.0.2 --source-digest $tagCommit
gh attestation verify SHA256SUMS.txt -R BARKx4/Ricochet --signer-workflow BARKx4/Ricochet/.github/workflows/release.yml --source-ref refs/tags/v1.0.2 --source-digest $tagCommit
gh release verify v1.0.2 -R BARKx4/Ricochet
gh release verify-asset v1.0.2 $asset -R BARKx4/Ricochet
Get-FileHash $asset -Algorithm SHA256

Compare the displayed hash with the exact asset entry in SHA256SUMS.txt. These release verification commands require publication and do not work on the draft.
