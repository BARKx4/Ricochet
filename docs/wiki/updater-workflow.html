Updater Workflow

Production-facing documentation for Ricochet developers.

On this page Channel Metadata Update Check Contract Rollback Story

Ricochet's production updater workflow is channel metadata plus platform verification. Ricochet 1.0 does not ship a self-replacing rco update command; installers, package managers, or a future elevated desktop updater can consume the same metadata without moving risky install privileges into the Ricochet runtime.

Channel Metadata

Stable tags from v1.0.1 publish UPDATE-CHANNEL-stable.json beside SHA256SUMS.txt. GitHub keyless attestations cover both files and every uploaded platform asset. Stable metadata requires github-attestation and sha256 for every target, plus Authenticode or Apple verification only when the signing report proves it was produced. Semver prerelease tags publish UPDATE-CHANNEL-candidate.json with dry-run SHA-256 metadata. The historical v1.0.0 release used GPG signatures.

pwsh -NoProfile -File ./scripts/write-update-channel.ps1 `
  -DistDir dist `
  -Channel stable `
  -Version 1.0.1 `
  -ReleaseTag v1.0.1 `
  -ReleaseUrl https://github.com/BARKx4/Ricochet/releases/tag/v1.0.1

The channel document records:

  • release version, tag, release URL, generation time, and rollout percentage.
  • rollback policy, currently reject-older-or-equal by default.
  • one platform entry per target: windows-x64, linux-x64, macos-arm64, and macos-x64.
  • each target's ARTIFACTS-<target>.json manifest hash and size.
  • primary archive, installer/package artifact, checksum file, signing report, optional notary report, required verification methods, and per-artifact SHA-256 metadata.

Validate channel metadata before publishing it:

pwsh -NoProfile -File ./scripts/validate-update-channel.ps1 `
  -DistDir dist `
  -Channel stable `
  -Version 1.0.1 `
  -RequireProduction

The release workflow writes and validates the channel document before writing SHA256SUMS.txt, attests their exact bytes, and verifies downloaded draft assets against the release workflow, tag ref, and peeled source commit before publication. The operator checks that immutable releases are enabled before tagging; after publication, GitHub's separate release attestation can be checked with gh release verify.

Update Check Contract

A Ricochet-compatible updater should:

  1. Fetch the channel file from an HTTPS release or channel URL.
  2. Verify the channel file's GitHub attestation against the expected repository, signer workflow, tag ref, and peeled source commit before trusting its metadata.
  3. Require schema = "ricochet.update-channel" and schema_version = 1.
  4. Require the expected channel name, such as stable or candidate.
  5. Reject channel versions less than or equal to the installed version unless the operator has explicitly chosen a manual rollback.
  6. Select the platform target for the current machine.
  7. Download the target manifest and all artifacts referenced by the selected platform entry.
  8. Verify the downloaded assets' GitHub attestations and every SHA-256 value against the channel metadata and target manifest.
  9. Run platform verification before install:
  • Windows: verify GitHub attestation and SHA-256; require Authenticode only when required_verification includes it, and check the explicit unsigned report otherwise.
  • Linux: verify GitHub attestations and SHA-256 for the tarball and Debian package; the package signing report records pending-attestation during packaging.
  • macOS: verify GitHub attestation and SHA-256; require codesign and accepted notarization only when those methods appear in required_verification, and check the explicit fallback report otherwise.
  1. Stage the new install outside the active installation path.
  2. Keep a backup of the previous install until the new rco --help or a stronger product smoke test succeeds.

Rollback Story

Automatic rollback means reverting from a failed staged install back to the previous local install. It does not mean silently downgrading from the public channel.

By default, channel consumers reject older or equal versions. Manual rollback uses the published GitHub release for the desired older version, then repeats its version-specific manifest, checksum, provenance, and platform checks before installing. The historical v1.0.0 rollback path requires its GPG verification instructions.

Updater state should live outside Ricochet VM images, application state, and project workspaces. A platform installer can keep its own backup directory or package-manager rollback metadata; Ricochet scripts should not delete an existing installation unless the updater has already staged and verified the replacement.
